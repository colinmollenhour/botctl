# Prompt handoff

`botctl` supports both direct TUI prompt execution and SQLite-backed prompt handoff through Claude's external-editor flow.

## Prompt paths

There are five supported paths:

1. **TUI-backed one-shot execution**
   - `prompt` launches Claude in a new detached tmux window, waits for `ChatReady`, pastes the resolved prompt into the interactive TUI through tmux, waits for the reply, and prints only assistant text to stdout. Pass `--verbose` for launch/wait progress on stderr. Arguments after `--` pass through to Claude.
   - Small inputs are pasted directly; inputs larger than `--large-prompt-threshold` are written to a state-dir instruction file and Claude receives a short prompt pointing at that file.

2. **Manual staging**
   - `prepare-prompt` writes prompt text to a workspace-scoped placeholder instance in the state database.
   - `editor-helper` reads that pending prompt from SQLite and writes it into the editor target path that Claude requested.

3. **New-text submission to an existing pane**
   - `submit-prompt --text ...` or `submit-prompt --source ...` resolves new text and submits it only after proving the target is `ChatReady` with an empty composer.
   - Add `--when-ready` for a bounded, synchronous, passive readiness wait.

4. **Existing-composer recovery**
   - `submit-composer` submits text already in the composer.
   - `clear-composer` destructively discards text already in the composer.

5. **Loop submission**
   - `keep-going` uses the built-in audit loop prompt by default.
   - `keep-going --source ...` or `keep-going --text ...` uses a custom loop prompt.

## State directory

The default state root is `$XDG_STATE_HOME/botctl` when `XDG_STATE_HOME` is set and non-empty. Otherwise, `botctl` uses `~/.local/state/botctl`.

`--state-dir PATH` overrides that root for commands that support it.

Relevant stateful commands bootstrap `<state-dir>/state.db`, run supported
schema migrations, and ensure the workspace, instance, and prompt-handoff
tables exist.

Manual prompt handoff uses the `pending_prompts` table, keyed by botctl instance
identity. `prepare-prompt` creates a placeholder instance for the selected
workspace and session, and `editor-helper` consumes or retains that pending
record. Direct `submit-prompt` and `keep-going` submissions do not create a
pending record: each uses one in-memory, ownership-checked staging transaction
against the exact pane.

Commands that support `--workspace PATH|UUID` accept either a botctl workspace id or a path. Path values may be absolute or relative; Git-backed paths collapse to the canonical worktree root, while non-Git paths use the resolved path itself as the workspace root.

The external editor target that Claude requests is still a regular file, but the staged prompt itself is no longer stored under a separate prompt path.

## `prompt`

`prompt` accepts repeated `--source`, one `--text`, explicit `--stdin`, implicit piped stdin, and repeated `--append-system-prompt`. It combines those inputs before launching Claude so input and filesystem errors fail early.

For large combined prompts, it creates `<state-dir>/prompt-runs/.../instructions.md` and pastes a short file-pointer prompt into Claude. Unless `--keep-temp` is set, the temp instruction file is removed after a successful response; with `--keep-temp`, the path is reported on stderr for debugging.

## `prepare-prompt`

`prepare-prompt` accepts either `--text` or `--source` and writes the resolved content to the selected workspace/session placeholder instance.

Use this when you want to stage content before the editor handoff begins.

## `editor-helper`

`editor-helper` is the bridge from staged prompt to Claude's editor target.

- with `--source`, it writes that source text directly to the target file
- without `--source`, it copies the pending prompt for the selected workspace/session into the target file
- by default it consumes the pending prompt record after copying
- `--keep-pending` leaves the staged prompt record in place

## Existing-pane submission and recovery

`submit-prompt` is for new text. Without `--when-ready`, it checks readiness
immediately. With `--when-ready`, it passively polls only the resolved pane
until two checks show `ChatReady` with an empty composer. It sends no key,
pastes no text, and writes no pending record during that wait.

After readiness, `submit-prompt`:

- validates that the target pane is Claude-owned
- verifies the live submit binding before paste
- pastes the prompt and waits for the complete visible composer to match
- submits through the user's binding and verifies an affirmative transition

It never clears failed, changed, merged, partial, or foreign composer text. A
readiness timeout exits `2` with `outcome=ready-timeout` and leaves the pane and
pending store unchanged. A staging or input-dead refusal retains the composer
for explicit inspection and recovery.

If text already exists, do not use `submit-prompt`. Inspect it, then run:

```bash
botctl submit-composer --pane %19
botctl clear-composer --pane %19
```

The second command is destructive. Both commands require occupied text in
`PromptEditing`, or a freshly confirmed ghost-shell condition with no other
busy evidence. Both revalidate the exact text and target, verify their
postcondition, refuse with exit `2` on `input-dead` or changed composer text,
and have no force mode. See the [command reference](./command-reference.mdx#submit-composer)
for complete outcomes and timeout behavior.
